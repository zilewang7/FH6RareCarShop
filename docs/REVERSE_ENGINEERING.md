# 逆向与实现思路

本文描述 FH6 奇珍商店工具从单活动实现演进为活动化基座的方法、运行时结构和失败边界。
仓库不包含游戏二进制、反编译产物、内存转储、存档或用户日志。

## 1. 活动不是一个固定的三槽商店

已验证活动具有不同结构：

| 活动 | 首次开放时间（UTC+8） | 槽数 | 每槽池大小 | 总车辆数 |
| --- | --- | ---: | ---: | ---: |
| 意大利奇珍 | 2026-07-16 22:30 至 2026-08-13 22:30 | 3 | 14 | 42 |
| 英国奇珍 | 2026-09-10 22:30 至 2026-10-08 22:30 | 2 | 11 | 22 |

这些时间用于区分活动首次出现的赛季，不决定游戏当前是否开放。工具把活动 ID、槽数、
每槽完整库存 ID 集合及 `库存 ID -> 车型 ID` 映射视为一份不可拆分的定义。GUI 默认
选择首次开放时间最新的定义，也允许查看历史目录。

写入前不会只检查车辆 ID。游戏进程中实际存在的所有目标槽都必须与所选活动定义匹配，
否则操作失败关闭。因此选择历史活动不会让其车辆出现在当前不同活动中。

## 2. 从可观察行为建立假设

完全退出游戏再进入场地会改变展示组合，但每个物理展位只会从自己的固定候选集合中
选车。存档文件没有出现与每次展示一一对应的稳定变化。由此建立两个可验证假设：

1. 当前展示主要保存在进程内活动状态，而不是持久化成一份固定库存。
2. 每个展位有自己的候选池、当前库存 ID、车型 ID 和刷新状态。

研究只比较进入场地前、进入后、刷新后和购买后的运行时状态。进程退出后临时改动全部
消失，这也是工具不触碰存档、货币和账号库存的边界。

## 3. 识别目录和车池

车辆目录由游戏资源中的 `AftermarketCars` 对象、字符串表、多次实际刷新结果及运行时
池数组交叉确认。英国活动当前得到两个互不重叠的 11 元素集合：

```text
左侧：200, 203, 206, 207, 208, 209, 210, 211, 215, 219, 220
右侧：199, 201, 202, 204, 205, 212, 213, 214, 216, 217, 218
```

附近还存在其它活动的 16 元素管理器，说明“找到类似对象”不足以判断活动。每个候选
展位管理器必须同时满足：

- 两个对象 vtable 都指向游戏主模块，已知版本还必须匹配对应 RVA 画像。
- `currentId` 属于该槽的完整车池。
- `pendingId` 为 `-1` 或同一车池中的合法 ID。
- 池的 `start/end/capacity` 指针有序、对齐，长度恰好等于该槽定义。
- 池中每个 ID 只出现一次，排序后与已验证集合完全相同。
- 当前车型 ID 与目录中的库存 ID 映射一致。

单个小整数、单个指针或单段机器码均不能独立成为写入依据。

## 4. Manager 快速定位与兼容回退

已验证游戏版本优先使用 manager 双 vtable RVA 画像。扫描器只读取已提交、可读写、
非 Guard 的私有内存，并按 allocation group 从最可能承载活动对象的主堆开始。一旦所选
活动的每个槽均得到唯一候选便提前结束。

当前 Xbox `3.440.853.0` 构建中，英国两槽可由同一画像约一秒定位。旧 Xbox 与 Steam
画像仍保留，避免升级通用活动后破坏意大利版本的快速路径。

未知版本回退过程为：

1. 搜索该槽完整的无序池集合，而不是搜索某一个车辆 ID。
2. 搜索指向候选池数组的引用。
3. 根据池字段偏移反推可能的管理器地址。
4. 使用前述全部结构不变量重新验证。
5. 每槽不是唯一候选时拒绝继续。

缓存键为 `PID + 进程启动时间 + 模块基址 + 活动 ID`。下一次操作仍会复核对象头、池和
当前车辆。若同一进程中已确认活动 A，随后请求活动 B，而 A 的缓存仍完整有效，工具会
直接报告活动不匹配，不再进入耗时的全堆回退。

## 5. 调用游戏自己的切换函数

观察当前 ID 变化时的调用路径，可以找到负责提交展位车辆的 setter。实现同时保存已
验证 RVA 和带通配字节的函数前导特征：

- 先检查已验证 RVA 处的机器码是否仍匹配。
- 不匹配时只扫描游戏主模块的可执行页面。
- 特征必须唯一命中；零个或多个命中都会停用写入。

调用时由最小 x64 stub 传入管理器、目标库存 ID，以及游戏原本使用的通知和依赖状态
重建参数。线程返回后重新读取 `currentId`、车型 ID 与 `pendingId`，直到状态稳定并再次
通过所选活动的管理器校验。

因此普通切换不是孤立地覆盖一个整数，而是调用游戏维护关联状态的原有路径。

## 6. 恢复购买资格和交互

购买后，车辆可能保留模型但失去购买入口，也可能连模型对应的交互状态一起卸载。资格
状态不在 manager 本体中，而在相邻关联的 SaveState 对象里。

解析流程如下：

1. 在目标 manager 附近查找对其地址的引用。
2. 在引用附近查找具有预期双 vtable 的 SaveState 对象。
3. 校验 SaveState 的 valid、invalid、eligible 虚函数均在游戏模块内。
4. 校验资格对象指针、布尔字段和值域。
5. 校验资格 getter 的机器码语义确实读取预期布尔偏移。
6. 只接受距离最近且唯一的关联结果。

恢复时先将资格布尔值置为可用，再调用游戏的 eligible 谓词验证。只写字节但谓词仍为
false 时立即停止。若目标交互已卸载，则先换到同活动、同槽池中的中转车，等待 SaveState
重新出现后再执行完整校验。

## 7. 为什么还需要完整刷新

仅恢复资格字节不能保证 UI 重新创建购买入口，完整链路还需要让游戏销毁并重建当前
展位交互：

1. 选择与目标和当前车辆都不同的第一辆同池中转车。
2. 临时把该槽候选池替换为一个经过活动目录验证的中转 ID。
3. 调用游戏自己的完整刷新函数。
4. 函数返回后立即恢复原始池边界与全部内容。
5. 验证游戏实际选中的中转车和 manager 稳定状态。
6. 通过 setter 切回目标车，重新解析 SaveState 并调用最终资格谓词。

临时单车池没有加入活动之外的车辆。从游戏刷新与工具日志能看到的行为仍是一次正常
随机选择，只是这次候选集合里只有一个合法成员，所以表现为正好“随机”到指定车辆。
最终结果与反复退出、重进直到随机命中相同，区别是省去了等待。

## 8. 事务与适配边界

重购事务记录原始车辆、原始池边界与内容、修改过的资格字节。正常失败时按相反顺序
回滚。远程游戏线程若超时且状态无法确认，强制释放 stub、恢复池或再次调用 setter 可能
与仍运行的线程竞争；此时工具停止强制回滚，并提示退出游戏清除进程内状态。

支持新活动或版本时应保留以下脱敏证据：

- 活动首次时间、物理槽顺序和每槽完整库存 ID 集合。
- 每个库存 ID 的车型 ID 映射。
- 游戏版本、发行渠道及 manager 唯一候选。
- setter、refresh 特征的唯一命中。
- SaveState、资格对象和 getter 的完整校验结果。
- 至少一次便宜车辆的“购买 -> 入口消失 -> 恢复 -> 再购买”实测。

不要提交用户存档、完整内存转储、游戏二进制、个人路径日志或访问令牌。研究结论应只
转化为最小活动目录、RVA 画像、签名、不变量和脱敏测试记录。
